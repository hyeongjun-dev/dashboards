1. 이슈 → 배포 리드타임
연결 0건
이슈 생성부터 프로덕션 배포까지 걸린 시간. 가장 중요한 속도 지표.
현재: 이슈 연결 0건 - Refs # 컨벤션 필요
클릭하여 상세 보기
세부 구간 4개:
(1) 이슈 생성 → PR 착수 (착수까지 대기)
(2) PR 생성 → staging 머지 (리뷰/수정, 현재 0~2h)
(3) staging 머지 → main 승격 (현재 최대 병목)
(4) main 머지 → Vercel 배포 (~4분, 자동)

공식: Production 배포 시점 - 이슈 생성 시점 (중앙값 + 상위 75%)
집계 대상: 이슈 유형 구분 없이 전체.
조작 방지: 이슈 생성 시점은 GitHub 자동 기록. "이슈 생성 시점 < 첫 커밋 시점" 조건 확인으로 소급 생성 탐지. 변경 파일 수(files changed)도 참고값으로 저장.
주의: feature PR은 staging 대상이라 Closes #가 이슈를 자동 종료하지 않음. Refs # 사용 후, 승격 PR에서 Closes #.

템플릿 정착 후
충분한 검증을 거쳐 머지된 PR의 비율. 검증 프로세스 성숙도.
현재: PR 템플릿 생성 완료, 정착 후 측정 시작
클릭하여 상세 보기
점수 기준 (4점 만점):
- 봇 또는 사람 리뷰 통과: 1점
- Vercel Preview 정상 배포: 1점
- 검증 체크리스트 완료: 1점
- 배포 후 7일 무사고: 1점
팀 지표 = 4점 중 3점 이상 비율

조작 방지: 실제 GitHub review event와 Vercel deployment status 확인. 작성자 외 1명 이상만 인정. [feat]/[bug]와 [chore]는 분모 분리.
단계별 강화: (1) 지금: PR 템플릿 체크리스트 (2) 다음: 고위험 PR 사람 리뷰 도입 (3) 이후: CI (typecheck + lint) 추가

오늘 논의 사항
1
승격 주기를 정하자
staging에 86커밋 적체. 주 2회(예: 화/금) 정기 승격만으로 가장 큰 병목이 해소됨. 이것 없이 다른 지표를 보는 건 의미가 없음.
2
사람 리뷰가 필요한 범위를 정하자
전체 필수 vs 고위험만(DB/인증/L사이즈). 봇 리뷰가 잘 돌고 있으니 범위를 좁히는 게 현실적. 봇 품질 문제가 생기면 그때 확대.
3
비개발자 기여는 어떻게 볼 것인가
PR 기반 지표로는 기획/운영/콘텐츠 기여가 안 잡힘. 월간 목표 리뷰에서 별도 확인이 현실적. 모든 기여를 하나의 판으로 억지로 묶을 필요 없음.

참고할 만한 흐름

DORA 메트릭만으로는 부족하다

배포빈도/리드타임/실패율/복구시간 - 가장 많이 쓰이는 지표이지만 한계가 명확
• DORA(배포빈도/리드타임/실패율/복구시간)는 "무엇이 일어났는지"만 보여줌. "왜"는 안 보여줌
• AI 도입 후 처리량은 30-40% 올랐지만, 변경 실패율도 15-25% 올라감
• 리뷰 없이 머지되는 PR이 전반적으로 증가하는 추세
• 소규모 팀에서 빡빡하게 적용하면 숫자 최적화에 집착 → 고객 가치 전달 소홀

결국 중요한 건 개발자 경험

코드 속도보다 프로세스 마찰이 실제 병목
AI가 코딩을 가속화하지만,
깨진 프로세스가 그 이득을 상쇄한다

소규모 팀이 볼 것 3가지:
• Flow State - 개발자가 중단 없이 집중할 수 있는가?
• Cognitive Load - 불필요한 복잡성이 없는가?
• Feedback Loops - 피드백 받는 데 얼마나 걸리는가?

DX Core 4

DORA를 보완하는 최신 프레임워크
• Speed - 엔지니어당 주간 처리량
• Effectiveness - 개발자 경험 만족도
• Quality - 변경 실패율 + 재작업률
• Business Impact - 배포된 기능의 실제 사용 여부

핵심 발견: DevEx가 좋은 팀이 DORA 지표도 4-5배 좋음
→ 원인(개발자 경험)을 관리하면 결과(지표)는 따라옴

팀 규모별 현실적 접근법

접근적합한 팀오버헤드
DORA 5개 지표 풀 트래킹50명+ 엔지니어링 조직높음
DX Core 420-50명, 전담 DevOps 있는 팀중간
분기 설문 + GitHub 기본 데이터15명 이하 스타트업 ← 우리낮음
병목 1개 제거 + 체감 관찰10명 이하, 초기 스타트업거의 없음

그래서 우리 팀에는?

15명 팀에 맞는 현실적 접근:

1. 가장 큰 병목 1개 제거 → staging 적체 해소 (승격 주기)
2. 분기 1회 팀 설문 3문항: "배포 과정이 복잡한가? / 피드백 받는 데 얼마나 걸리나? / 도구가 불편한 곳은?"
3. GitHub 기본 데이터 월 1회 확인: PR 처리 속도, hotfix 비율 (이미 볼 수 있음)
4. 나머지는 팀이 성장하면 그때 추가

지표 시스템을 새로 구축하는 것보다, 프로세스 병목 제거 + 분기 설문이 15명 팀에 현실적.
